# TOS（Tofu POS v3）

オンライン前提の最小のネイティブレジ。AndroidはKotlin・Jetpack ComposeとMaterial 3 Expressive、iOSはSwiftUI。会計は端末で完結し、売上と取消は会計のたびに自動でCloudflareへ同期します（通信できなくても会計は端末に保存）。端末DBは両OSのSQLiteを使用します。

## 今できること

- 商品登録・商品名と価格の変更
- 商品選択・数量変更・預り金入力・釣銭計算・会計確認
- SQLiteへの会計と明細の一括保存
- 注文履歴・理由と返金確認を伴う全額取消
- 全期間の売上合計・全明細CSVの保存
- Cloudflare Workers・D1への自動差分同期（「今すぐ送信」で手動も可）、未同期件数・保留表示
- 商品の日時つきバックアップ、別端末への商品・売上・取消の復元

会計確定は端末のコミットで成立します。同じ会計IDの再実行では二重計上せず、同じIDで異なる内容は拒否します。取消後も元の会計を残します。価格変更は過去の会計・選択済みカートに影響しません。

定期ポーリングはありません。同期は会計・取消の確定後、起動・前面復帰時、接続設定の保存後に自動で1回ずつ実行します。読み込みは起動時と明示操作の完了時のみ。AndroidはDB操作を単一ワーカースレッドへ直列化し、通信は別スレッドで実行します。iOSも通信の応答待ちで会計を止めません。

在庫・金種・割引・顧客属性・整理券・締め・キッチン・呼出・ユーザーアカウントは未実装です。CSVは分析用です。クラウドへ保存した商品と成立済み会計は復元できますが、接続設定と入力中のカートはバックアップしません。

## Cloudflare同期

Androidは「同期」、iOSは「履歴・売上」から同期設定を開き、レジ専用のJSON設定ファイル（`url`・`token`）を読み込みます。手入力も可能です。Cloudflare管理用APIトークンをアプリに入れないでください。端末用トークンはiOS Keychain／Android Keystoreで保護して保存します。

1回の送信は最大50注文・256KiB。残りがあれば5秒後に自動で続きを送ります。「今すぐ送信」でも同じ処理を手動実行でき、重複タップや自動送信と並列起動しません。通信・サーバーの失敗は下記の待機時間が過ぎたらアプリが前面にある間だけ自動再送し、401／403と内容競合は自動再送せず次の会計か手動実行を待ちます。失敗時は15〜300秒の指数バックオフとjitter、HTTP Retry-Afterは最大1時間を反映し、アプリ再起動後も待機を維持します。401／403では設定確認を促して5分以上待機します。通信は25秒で打ち切り、会計は継続できます。

同期するのは成立済みの注文・明細・取消です。商品マスタ、入力中カート、在庫、顧客情報は送信しません。ローカルDBはv1からv2へデータを保持して移行します。既存注文は未同期になり、過去の取消はrevision 2で送信します。送信中に取消された場合も古いrevision 1の応答では取消を同期済みにしません。

同期済み判定はサーバーが返した注文IDとrevisionの組だけを使います。同期先URLを変更すると誤って別DBへ混在するため、初回設定後の変更は禁止しています。トークン更新は同じURLのまま可能です。1注文が256KiBを超える場合は端末内に保留し、ほかの注文の同期を妨げません。保留は未同期件数に含め、CSVで救出できます。

サーバーは1店舗用で、店舗IDはWorkers設定の`SHOP_ID`（現在`tofu`）から決まります。トークンに対応する店舗以外をリクエストで指定できません。原会計の金額・明細は変更不可で、同一revisionの異なる内容は競合として残します。正常な同一再送ではD1を読み取るだけで書き込みません。最大50件でも初回は対象IDの検索1回＋更新後確認1回、同一再送は検索1回です。定期的な全件読み取りやテレメトリのDB保存は行いません。

現在の保存先はCloudflare D1 **`tofu-pos-v3` → `cloud_orders`**。注文ごとの最新状態を1行に保持し、`payload`に明細を含むJSON、`revision`に1または2、`cancelled`に取消フラグを保持します。集計時は`shop_id`で絞り、取消を売上から除外します。商品バックアップは`cloud_catalogs`へ不変スナップショットとして保存します。

同期API: `https://tofu-pos-v3-sync.gapul.workers.dev/v1/sync`。API本文は`schema_version=1`と`orders`配列。認証なしの要求は401で拒否します。

サーバーのテスト・配備手順は[cloudflare/README.md](cloudflare/README.md)を参照してください。

## バックアップ・復元

売上・取消は自動で送信されます（営業後に未同期0件を確認）。商品を変更したときは「商品をバックアップ」も実行します。商品は最大1000件・256KiBのスナップショットとして保存。同じ内容の再保存でD1を書き直さず、空の端末から保存しても過去のバックアップを消しません。

新しい端末に同じ店舗の接続設定を入れ、「クラウドから復元」で商品バックアップを選択します。日時はJST、新しい順に20件ずつ表示し、「さらに表示」で過去分も選択できます。「売上のみ復元」も可能です。選択した商品スナップショットと、現在クラウドに保存されている売上・取消を取り込みます。

売上は1操作で最大50件、合計明細サイズも制限します。「続きがあります」と出たら「売上の続きを復元」を押してください。読み出しの完了を確認する最後のページが空の場合もあります。カーソルと累計件数は取り込むページと同じ端末内トランザクションに保存し、終了・回転後も続行できます。途中の通信失敗ではそのページを取り込まず、バックオフ後に同じ位置から再開します。

同じIDの同じ商品・会計は重複追加しません。異なる商品名・価格・原会計の内容・取消理由は上書きせず、競合の累計件数を表示します。既存のローカル取消は古い会計で元に戻さず、クラウドの新しい取消は元会計の一致を確認して反映します。商品価格を復元しても過去単価や入力中カートは変えません。

復元は複数ページにまたがる全体の一点時点スナップショットではありません。別端末で更新中のときは営業終了後に送信を完了し、必要に応じて先頭から復元を再実行してください。バックアップしていない端末内だけのデータや、サイズ超過で未送信の会計は復元できません。端末用の接続設定ファイルは、端末が故障しても取り出せる場所に保管してください。

通信は売上同期・バックアップ・一覧・復元の間で単一実行。自動再送・ポーリング・自動ページ取得はしません。復元応答は最大約516KiB（商品約256KiB＋会計約256KiB＋ヘッダー）で、注文・商品と応答の形式を端末でも検証します。ローカルDBのバージョンは2のままで、既存データの移行や削除はありません。

## Android

必要環境: JDK 17以上、Android SDK 36、Build Tools 35.0.0。端末はAndroid 8.0（API 26）以上。

```sh
cd android
./gradlew testDebugUnitTest assembleDebug lintDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

アイコンは「Are you Tofu?」の「Tofu」のoの豆腐を使用。元データと色の出典は[shared/branding](shared/branding/README.md)を参照してください。

Material 3 Expressiveの`MaterialExpressiveTheme`・`ButtonShapes`・`LoadingIndicator`を使用します。既存AGP 8.10.1と互換性のある`material3:1.5.0-alpha18`を固定しています（先行版）。横画面・キーボード表示・大きな文字では固定会計欄をスクロール内へ移し、入力欄の高さを確保します。

APK: `android/app/build/outputs/apk/debug/app-debug.apk`。同期用にINTERNET権限を使用しますが、会計に接続は不要です。商品・会計はアプリ専用SQLiteへ保存し、CSVはOSの保存先選択画面から書き出します。テスト時の機内モードでは端末内の保存先を選んでください。

専用エミュレータでDBテスト。Gradleは試験後にアプリを削除するため、営業データのある実機を使わないでください。シリアル番号未指定の実行はガードで停止します。

```sh
cd android
ANDROID_SERIAL=emulator-5582 ./gradlew connectedDebugAndroidTest
```

## iOS

必要環境: 完全なXcode、iOS SDK、XcodeGen。iOS 16以上を対象とします。

```sh
cd ios
xcodegen generate
open TofuPOS.xcodeproj
```

XcodeでTofuPOSスキームを選択し、シミュレータまたは署名チームを設定した端末へ実行してください。署名・TestFlight配布は未設定です。

接続済みiPhoneの遠隔インストール・起動・ログ取得は[docs/ios-device.md](docs/ios-device.md)を参照してください。確認済み経路はTailscale SSH → Mac mini → USB → iPhoneです。

会計・SQLite部分はOS UIから独立しており、Mac上でも検証できます。

```sh
swift test
# XCTestのないCommand Line Tools環境では以下で実DB検証:
sh scripts/verify-swift-core.sh
```

## 検証した性質

- 整数円、数量1〜999、会計と預り金は0〜1,000,000,000円
- 預り不足・不正数値・会計金額超過を拒否
- ファイルDBを閉じて開き直しても商品・会計・価格スナップショットを保持
- 同じ会計を100回要求しても1注文、内容が異なる再利用は拒否
- 2つ目の明細書き込みを故障注入すると注文全体がロールバック
- 全額取消後も元注文を保持し、二重取消を拒否
- 両OSのCSVは `shared/golden-sales.csv` とバイト単位で一致
- CSVの商品名の改行・引用符・数式文字を安全に書き出し

XCTestの実行にはXcodeのテストライブラリが必要です。CLTのみの環境では上記の代替検証を使います。MacBookのXcode 27.2で実機向けビルドとXCTest 17件の成功を確認済みです。iOSの実機上の動作は別途確認してください。

署名用の既存プロファイル・証明書がある場合、Xcodeで作成したアプリを `python3 scripts/package-ios.py APP PROFILE IDENTITY_SHA1 OUTPUT_IPA` で署名・検証してIPA化できます。プロファイル・秘密鍵・IPAはリポジトリに含めません。

## 手動確認

1. 機内モードで起動し、「商品」で豆腐500円・別商品100円を登録。
2. レジで豆腐を2個、別商品を1個選択。預り2000円で釣銭900円を確認し確定。
3. 履歴の全期間売上が1100円、会計1件であることを確認。
4. アプリを強制終了して再起動し、会計・明細・釣銭が残ることを確認。
5. 商品価格を変更しても過去の単価が変わらないことを確認。
6. 履歴から全額返金を確認して理由を入力し取消。売上0円・取消1件・元明細保持を確認。
7. CSVを端末内へ保存し、取消行と `net_line_sales_yen=0` を確認。

## CSV

UTF-8 BOM・CRLF・1明細1行。時刻はUTC（画面はJST）。`order_total_yen`、`received_yen`、`change_yen` は注文の先頭明細にのみ出し、重複加算を防ぎます。`line_total_yen` は元明細額、`net_line_sales_yen` は取消なら0円。取消行を消しません。注文IDはUUIDで整理券番号ではありません。

## 構成

- `ios/Core`: 金額計算、SQLite、CSV
- `ios/App`: SwiftUI画面
- `ios/Tests`: XCTestによる会計・永続化・故障注入検証
- `android/app`: Kotlin画面・SQLite・会計・CSV・テスト
- `shared/golden-sales.csv`: 両OS共通の期待値
- `scripts/verify-swift-core.sh`: CLTのみで実行できるSQLite検証

初版の仕様はこのREADMEとテストに限定します。先に作成した広いv3仕様案の機能を、この最小版の必須条件として扱いません。
